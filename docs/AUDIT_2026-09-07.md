## 1. ERROS E BUGS

### E-01: 🟠 Alto — websearch import name wrong
**Ficheiro:** `superai/shortcuts.py:28`
**Problema:** `from .websearch import search` mas a função chama-se `websearch()`. Causa `ImportError` em runtime.
**Impacto:** Endpoint `/api/web/search` e shortcut de pesquisa web falham.
**Comando:** `grep -n "from .websearch import" superai/shortcuts.py`
**Solução:** Alterar para `from .websearch import websearch` e ajustar a chamada.

### E-02: 🟡 Médio — Mutable default arguments
**Ficheiro:** `server.py:683, 724, 735`
**Problema:** `def api_gods_save(body: GodIn, ...)` e outros endpoints usam `body: dict = {}`. Dict mutável como default é partilhado entre chamadas.
**Impacto:** Baixo na prática (FastAPI cria novo dict por request), mas é anti-pattern.
**Solução:** Usar `body: dict | None = None` e tratar `None` como `{}`.

### E-03: 🟡 Médio — Prompt caching split pode falhar
**Ficheiro:** `superai/providers.py` (Anthropic + OpenAI compat)
**Problema:** O split em `"\n\nUSER: "` assume que o prompt sempre contém esse marcador. Se o `_llm_prompt` mudar o formato, o split falha silenciosamente.
**Impacto:** Prompt caching deixa de funcionar, o prompt inteiro vai como user message.
**Solução:** Já tem fallback (usa prompt inteiro como user message). Melhorar logging quando o split não acontece.

### E-04: 🟡 Médio — Qdrant payload index warning em local mode
**Ficheiro:** `superai/memory_vec.py:66`
**Problema:** `create_payload_index()` emite warning em Qdrant local (embedded). O código já tem try/except, mas o warning polui os logs.
**Impacto:** Nenhum funcional. Cosmético.
**Solução:** Verificar se é Qdrant server antes de criar índice, ou suprimir warning.

### E-05: 🟢 Baixo — `_intent_cache` não é thread-safe
**Ficheiro:** `superai/brain.py`
**Problema:** `_intent_cache` é um dict global modificado sem lock. Em teoria, duas threads podem escrever simultaneamente.
**Impacto:** Baixo — worst case é recomputar embeddings uma vez extra.
**Solução:** Usar `threading.Lock` ou aceitar o race condition benigno.

### E-06: 🟢 Baixo — `_pattern_counts` em thirdeye não é thread-safe
**Ficheiro:** `superai/thirdeye.py`
**Problema:** `_pattern_counts` é dict global sem lock.
**Impacto:** Baixo — worst case é contar mal um padrão.
**Solução:** Aceitar (race condition benigno) ou adicionar lock.

## 2. SEGURANÇA

### S-01: 🟠 Alto — Endpoints sensíveis sem rate limiting
**Ficheiro:** `server.py`
**Problema:** `/api/chat`, `/v1/chat/completions`, `/api/auth/setup`, `/api/auth/login` não têm rate limiting.
**Impacto:** Atacante pode fazer brute-force no login ou spam no chat.
**Solução:** Adicionar rate limiting via middleware ou dependency injection.

### S-02: 🟠 Alto — Error messages podem vazar info interna
**Ficheiro:** `superai/providers.py` (4 ocorrências)
**Problema:** `str(e)` em respostas de erro pode incluir stack traces, paths, ou credenciais.
**Impacto:** Informação exposta ao utilizador.
**Solução:** Truncar erros a100 chars e não incluir paths.

### S-03: 🟡 Médio — CORS allow_origins=["*"]
**Ficheiro:** `server.py`
**Problema:** CORS permite qualquer origem. Aceitável em rede local, mas se exposto à internet é um risco.
**Impacto:** Cross-origin requests de qualquer site.
**Solução:** Documentar que é intentional para local-first, ou restringir a origins conhecidas.

### S-04: 🟡 Médio — 76 silent exceptions
**Ficheiro:** Múltiplos (ver análise AST)
**Problema:** `except Exception: pass` em76 pontos do código. Erros são engolidos sem logging.
**Impacto:** Bugs difíceis de diagnosticar. Falhas silenciosas.
**Solução:** Adicionar `log.debug()` ou `log.warning()` nos catches mais importantes.

### S-05: 🟡 Médio — Worker token em env var
**Ficheiro:** `server.py:52`
**Problema:** `WORKER_TOKEN = os.environ.get("SUPERAI_WORKER_TOKEN") or ""` — token em string vazia se não definido.
**Impacto:** Se token não definido, workers remotos são rejeitados (correcto), mas sem logging.
**Solução:** Log warning se token não definido e workers remotos tentam ligar.

### S-06: 🟢 Baixo — JSONResponse em error handler
**Ficheiro:** `server.py:311, 319`
**Problema:** Error handler usa `JSONResponse` em vez de `ORJSONResponse`.
**Impacto:** Negligível — erros são raros.
**Solução:** Trocar para `ORJSONResponse`.

## 3. PERFORMANCE

### P-01: 🟡 Médio — 125 endpoints síncronos
**Ficheiro:** `server.py`
**Problema:** Apenas5 de130 endpoints são `async def`. Os125 restantes são `def` síncronos, bloqueiam thread pool.
**Impacto:** Sob carga, o thread pool pode saturar. Async é 6-7x mais rápido para I/O.
**Solução:** Converter endpoints que fazem I/O para `async def`. Prioridade: `/api/state`, `/api/chat`, `/api/health/deep`.

### P-02: 🟡 Médio — SSE sem heartbeat
**Ficheiro:** `server.py:931, 1093`
**Problema:** SSE streams não enviam heartbeat. Conexões podem ser cortadas por proxies/load balancers.
**Impacto:** Conexões SSE instáveis atrás de reverse proxies.
**Solução:** Enviar `:heartbeat\n\n` a cada30s.

### P-03: 🟡 Médio — Embedding recomputa em classificação
**Ficheiro:** `superai/brain.py`
**Problema:** `_classify_by_embedding()` computa embeddings para exemplos de intenção na primeira chamada. O cache existe mas é global.
**Impacto:** Primeira classificação é lenta (~100ms). Subsequentes são rápidas.
**Solução:** Já resolvido com warmup no boot. Verificar que o warmup está a correr.

### P-04: 🟡 Médio — `health_all()` chamado múltiplas vezes por pipeline
**Ficheiro:** `superai/pipeline.py`, `superai/routing.py`
**Problema:** `health_all()` é chamado em `run_pipeline()` E em `routing.complete()`. Com cache de10s, a segunda chamada é grátis, mas sem cache seria2x probes.
**Impacto:** Baixo com cache. Potencialmente lento sem cache.
**Solução:** Já mitigado com cache de10s.

### P-05: 🟢 Baixo — `_build_conversation_summary()` corre em cada `_dialogue()` call
**Ficheiro:** `superai/runtime.py`
**Problema:** A cada chamada de `_dialogue()`, `_build_conversation_summary()` analisa o chat inteiro.
**Impacto:** ~1-5ms por chamada. Aceitável.
**Solução:** Cachear summary com TTL de30s.

### P-06: 🟢 Baixo — `normalize_query()` chamado repetidamente
**Ficheiro:** `superai/brain.py`
**Problema:** `normalize_query()` é chamado em `cache_lookup()`, `cache_store()`, e `embed()`. Mesma computação repetida.
**Impacto:** Negligível (<1ms).
**Solução:** Cachear resultado de `normalize_query()` no request.

### P-07: 🟢 Baixo — `_extract_files()` usa regex pesado
**Ficheiro:** `superai/pipeline.py`
**Problema:** `_extract_files()` faz regex parsing de todo o texto LLM para encontrar fences.
**Impacto:** Negligível para textos <10KB.
**Solução:** Nenhuma necessária.

## 4. ROBUSTEZ

### R-01: 🟠 Alto — Pipeline sem timeout global
**Ficheiro:** `superai/pipeline.py`
**Problema:** Se o LLM call ficar pendurado (timeout não aplicado), o pipeline bloqueia indefinidamente.
**Impacto:** Thread bloqueada, utilizador sem resposta.
**Solução:** Adicionar timeout global de30s ao pipeline. Os providers já têm timeouts individuais, mas o pipeline como um todo não tem.

### R-02: 🟡 Médio — Thread pool size fixo
**Ficheiro:** `superai/pipeline.py:807`
**Problema:** `ThreadPoolExecutor(max_workers=2)` para cache + memory. Se uma das tasks ficar pendurada, a outra fica à espera.
**Impacto:** Pipeline pode bloquear se memory search ficar lenta.
**Solução:** Usar `asyncio.to_thread()` ou aumentar workers para3.

### R-03: 🟡 Médio — `run_in_executor` sem timeout
**Ficheiro:** `server.py:904`
**Problema:** `await loop.run_in_executor(None, lambda: handle(...))` sem timeout. Se `handle()` bloquear, o endpoint fica pendurado.
**Impacto:** Conexão SSE mantida indefinidamente.
**Solução:** Usar `asyncio.wait_for()` com timeout de30s.

### R-04: 🟡 Médio — Background threads sem graceful shutdown garantido
**Ficheiro:** `superai/autonomous_learner.py`, `superai/idle_worker.py`, `superai/knowledge_auditor.py`
**Problema:** Threads background usam `time.sleep()` para intervalos. O shutdown signal (`_running = False`) só é verificado após o sleep completar.
**Impacto:** Shutdown pode demorar até o intervalo do ciclo (30-60s).
**Solução:** Usar `threading.Event.wait(timeout)` em vez de `time.sleep()`.

### R-05: 🟡 Médio — SQLite connection não verificada após reconnect
**Ficheiro:** `superai/store.py`
**Problema:** Se a conexão SQLite for perdida (ex: WAL corruption), o `_get_conn()` retorna a conexão cached sem verificar se ainda está válida.
**Impacto:** Erros "database is locked" ou "database disk image is malformed" não recuperam automaticamente.
**Solução:** Adicionar `SELECT 1` health check antes de retornar conexão cached.

### R-06: 🟢 Baixo — `events.py` history não persiste
**Ficheiro:** `superai/events.py`
**Problema:** Event history é in-memory. Após restart, o histórico é perdido.
**Impacto:** Dashboard perde eventos após restart.
**Solução:** Persistir últimos100 eventos em SQLite (opcional).

### R-07: 🟢 Baixo — `_bcast_timer` pode leak se shutdown rápido
**Ficheiro:** `superai/runtime.py`
**Problema:** `_bcast_timer` é um `threading.Timer` que pode não ser cancelado no shutdown.
**Impacto:** Timer executa após shutdown, tenta broadcast para objetos já fechados.
**Solução:** Já tem try/except no `fire()`. Aceitável.

### R-08: 🟢 Baixo — Knowledge graph seed é síncrono
**Ficheiro:** `superai/runtime.py` (boot)
**Problema:** `seed_knowledge()` corre no warmup thread, mas é síncrono e pode demorar.
**Impacto:** Boot mais lento se knowledge graph precisar de seed.
**Solução:** Já está em background thread. OK.

## 5. ARQUITECTURA

### A-01: 🟡 Médio — Funções >100 linhas (11 ocorrências)
**Ficheiros:** autonomous_learner (344L), idle_worker (229L), knowledge_auditor (362L), providers (111L), routing (109L), websearch (536L)
**Problema:** Funções muito longas são difíceis de testar, manter e depurar.
**Impacto:** Manutenibilidade reduzida.
**Solução:** Extrair sub-funções. Prioridade: `_loop()` em autonomous_learner e knowledge_auditor.

### A-02: 🟡 Médio — Circular import pipeline→runtime
**Ficheiro:** `superai/pipeline.py:554`
**Problema:** `pipeline.py` importa de `runtime.py` (callbacks como `_say`, `_broadcast`). Isto é resolvido via dependency injection (callbacks passados como parâmetros), mas é frágil.
**Impacto:** Se alguém adicionar import direto, circular import crash.
**Solução:** Manter o pattern actual (dependency injection). Documentar.

### A-03: 🟡 Médio — 130 endpoints num só ficheiro
**Ficheiro:** `server.py` (1612 linhas)
**Problema:** Todos os endpoints estão num só ficheiro. Dificulta navegação e testes.
**Impacto:** Manutenibilidade.
**Solução:** Extrair para routers (FastAPI APIRouter). Prioridade: auth, system, providers.

### A-04: 🟢 Baixo — Duplicação de lógica em providers
**Ficheiro:** `superai/providers.py`
**Problema:** Cada adapter (Ollama, OpenAI, Claude, Gemini) tem lógica similar de health check, error handling, e response parsing.
**Impacto:** Código repetido.
**Solução:** Extrair helper methods para a classe base `Provider`.

### A-05: 🟢 Baixo — `_llm_prompt` em runtime.py mas lógica em brain.py
**Ficheiro:** `superai/runtime.py`
**Problema:** `_llm_prompt` está em runtime.py mas chama `brain.detect_user_style()`. A separação não é clara.
**Impacto:** Confusão sobre onde está a lógica do prompt.
**Solução:** Mover `_llm_prompt` para brain.py (já temos `detect_user_style` lá).

### A-06: 🟢 Baixo — Feature flags não documentadas no código
**Ficheiro:** `superai/feature_flags.py`
**Problema:** Flags como `semantic_cache`, `auto_learning`, etc. são definidas mas não há docs sobre quando usar cada uma.
**Impacto:** Dificulta debugging.
**Solução:** Adicionar docstring a cada flag.

### A-07: 🟢 Baixo — Testes não cobrem pipeline completo
**Ficheiro:** `tests/`
**Problema:** Testes cobrem componentes individuais (security, brain, auth) mas não o pipeline end-to-end.
**Impacto:** Regressões no fluxo completo não detetadas.
**Solução:** Adicionar testes de integração com mock LLM.

## 6. SERVIDOR E LIGAÇÕES

### L-01: 🟠 Alto — SSE connections sem limite
**Ficheiro:** `server.py:931, 1093`
**Problema:** Não há limite no número de conexões SSE simultâneas. Cada conexão mantém uma thread.
**Impacto:** Atacante pode esgotar threads com muitas conexões SSE.
**Solução:** Limitar a10 conexões SSE por IP.

### L-02: 🟡 Médio — GZip não se aplica a SSE
**Ficheiro:** `server.py`
**Problema:** GZip middleware não comprime SSE streams (chunks pequenos).
**Impacto:** Nenhum — SSE são eventos pequenos.
**Solução:** Nenhuma necessária.

### L-03: 🟡 Médio — Proxy buffering pode atrasar SSE
**Ficheiro:** `server.py`
**Problema:** `X-Accel-Buffering: no` já está presente ✅. Mas `Cache-Control: no-cache` pode não ser suficiente para todos os proxies.
**Impacto:** SSE pode ter latência extra atrás de Nginx/Cloudflare.
**Solução:** Adicionar `Connection: keep-alive` explicitamente (já presente no stream principal).

### L-04: 🟢 Baixo — Health check faz snapshot completo
**Ficheiro:** `server.py` (`/api/state`)
**Problema:** `/api/state` chama `snapshot()` que faz health checks a todos os providers, Qdrant, SQLite, etc.
**Impacto:** Endpoint pesado (~100-500ms). Não adequado para health checks frequentes.
**Solução:** Já existe `/api/health` leve. Documentar a diferença.
